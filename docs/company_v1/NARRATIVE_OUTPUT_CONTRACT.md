# 회사편 v1 서사 출력 및 렌더링 계약

상태: active design contract  
기준일: 2026-08-03  
적용 시점: Story/Frontend 구현 단계. Phase 0에는 구현하지 않는다.

## 1. 목적

서사 문장과 캐릭터 대사가 한 덩어리의 긴 텍스트로 출력되면 다음 문제가 생긴다.

- 누가 말했는지 빠르게 파악하기 어렵다.
- 서사와 대사를 UI에서 다르게 표시하기 어렵다.
- TTS가 서사와 대사를 정확히 분리하기 어렵다.
- 다중 NPC 장면에서 발화자 추적이 흔들린다.
- 스트리밍 중 문단이 완성되기 전까지 렌더링 기준이 불명확하다.

회사편은 시간 순서를 유지하면서 서사와 대사를 명시적인 블록으로 구분한다.

## 2. 핵심 원칙

1. 장면의 시간 순서는 유지한다.
2. 서사와 대화를 각각 별도 블록으로 표시한다.
3. 모든 대화에는 발화자와 연기 지시가 있다.
4. 모델 출력은 사람이 읽을 수 있고 기계적으로도 파싱 가능해야 한다.
5. 파싱 실패 시 원문을 잃지 않는 fallback이 있어야 한다.
6. Story SSE는 그대로 스트리밍하며 완료 후 별도 LLM 재작성은 하지 않는다.
7. TTS는 dialogue block만 기본 대상으로 한다.

## 3. 권장 Story 원문 형식

### 3.1 본문은 순서가 있는 블록

```text
[SCENE]
오후 햇빛이 블라인드 사이로 길게 들어왔다. 회의실 안에는 아직 발표 자료가 떠 있었다.

[DIALOGUE speaker="김하연" direction="자료를 내려다보다가 조심스럽게 고개를 들며"]
“수정안은 봤어요. 그런데 이 부분은 대표님께 다시 확인해야 할 것 같아요.”

[SCENE]
김하연은 태블릿을 플레이어 쪽으로 돌려 문제의 문장을 가리켰다.

[DIALOGUE speaker="김하연" direction="목소리를 낮추며"]
“지금 바로 올라가실 건가요?”
```

- `[SCENE]`은 서술, 행동, 환경, 비언어 반응을 담는다.
- `[DIALOGUE ...]`는 캐릭터의 실제 발화만 담는다.
- 같은 발화자의 연속 대사도 각 발화 단위로 구분한다.
- 플레이어가 실제로 말하지 않은 대사를 Story가 임의 생성하지 않는다.

### 3.2 후속 섹션

본문 블록 뒤에 다음 섹션을 둔다.

```text
[PLAYER_STATUS]
현재 위치: 5층 소회의실
현재 업무: 캠페인 수정안 검토
현재 상황: 김하연이 대표이사 확인이 필요한 문장을 보여주고 있다.

[CHOICES]
1. 김하연과 함께 수정안을 다시 검토한다.
2. 대표이사실에 같이 올라가자고 제안한다.
3. 현재 적용 규정을 이용해 보고 자세를 요구한다.
4. 다른 방식으로 직접 행동한다.
```

`PLAYER_STATUS`는 서사를 반복하지 않고 플레이어가 다음 행동을 판단하는 데 필요한 현재 상태만 짧게 정리한다.

## 4. 블록별 계약

### 4.1 SCENE

포함 가능:

- 배경
- 인물 행동
- 표정
- 시선
- 자세
- 물리적 변화
- 주변 NPC 반응
- 장면 전환

포함 금지:

- 실제 발화 문장을 따옴표로 삽입
- 내부 검증 지시
- 확률 계산 과정
- 저장 필드명
- 모델 메타 설명

### 4.2 DIALOGUE

필수 속성:

- `speaker`
- `direction`

본문 규칙:

- 실제 대사만 한국어 따옴표 안에 작성
- 한 블록에 한 발화자
- 발화자 이름은 등록 캐릭터 또는 현재 장면에 허용된 일반 NPC
- `direction`은 짧고 시각적으로 이해 가능한 연기 지시
- 감정 이름만 나열하지 말고 행동 또는 목소리 특징으로 쓴다.

예:

```text
[DIALOGUE speaker="윤아름" direction="입술을 꾹 다문 채 서류를 건네며"]
“이건 제가 다시 정리하겠습니다.”
```

금지:

```text
[DIALOGUE speaker="윤아름" direction="슬픔, 화남, 긴장"]
```

### 4.3 PLAYER_STATUS

권장 길이: 120~240자.

포함:

- 현재 장소
- 현재 시간대
- 현재 업무 또는 장면 목표
- 플레이어의 직접 행동에 영향을 주는 물리 상태
- 즉시 주의해야 하는 pending 상태

포함 금지:

- 모델의 성공률 예측
- 숨겨진 NPC 생각
- 다음 Story를 강제하는 지시
- 장황한 지난 줄거리

### 4.4 CHOICES

- 기본 4개
- 번호 1~4
- 선택지마다 하나의 핵심 행동
- 복합 행동 묶음 최소화
- 내부 분류명은 원문에 노출하지 않는다.
- 전체 원문은 저장하고 UI 버튼에서는 최대 2줄로 축약 가능하다.

## 5. UI 렌더링

### 5.1 SCENE 표시

- 일반 본문 글꼴
- 문단 사이 충분한 간격
- 카드 테두리 없이 자연스러운 소설 본문 형태
- 최대 읽기 폭 720~800px

### 5.2 DIALOGUE 표시

대화는 명확한 speech block으로 렌더링한다.

```text
김하연
자료를 내려다보다가 조심스럽게 고개를 들며
“수정안은 봤어요. 그런데 이 부분은 대표님께 다시 확인해야 할 것 같아요.”
```

권장 시각 요소:

- 발화자 이름 강조
- 연기 지시는 작은 보조 텍스트
- 대사는 본문보다 약간 높은 대비
- 등장인물별 고정된 과도한 색상 사용은 피한다.
- 이미지가 있는 경우 작은 avatar는 선택 사항이며 필수는 아니다.

### 5.3 플레이어 입력 표시

플레이어가 선택하거나 직접 입력한 행동은 다음 Story 시작 전에 별도 action chip으로 표시한다.

```text
내 행동
대표이사실에 같이 올라가자고 제안한다.
```

플레이어 행동을 NPC 대화 카드와 같은 형식으로 표시하지 않는다.

## 6. 스트리밍 처리

### 6.1 원칙

- Worker는 upstream SSE body를 직접 반환한다.
- Frontend parser는 들어오는 텍스트를 누적하면서 marker를 인식한다.
- 완료되지 않은 블록은 임시 buffer로 둔다.
- marker가 닫히거나 다음 marker가 시작되면 블록을 확정한다.

### 6.2 표시 우선순위

- 완성된 SCENE 문장은 즉시 표시 가능
- DIALOGUE header가 확인되면 발화자 영역을 만든다.
- 닫는 따옴표가 아직 없어도 streaming text는 해당 대화 영역 안에서 이어서 표시한다.
- 스트리밍 중 자동 하단 이동을 강제하지 않는다.
- 사용자가 이미 최하단 근처에 있을 때만 부드럽게 따라간다.

## 7. 파서 결과 구조

Frontend 내부 표현 예시:

```json
{
  "blocks": [
    {
      "type": "scene",
      "text": "오후 햇빛이 블라인드 사이로 길게 들어왔다."
    },
    {
      "type": "dialogue",
      "speaker": "김하연",
      "direction": "자료를 내려다보다가 조심스럽게 고개를 들며",
      "text": "수정안은 봤어요. 그런데 이 부분은 대표님께 다시 확인해야 할 것 같아요."
    }
  ],
  "player_status": "...",
  "choices": ["...", "...", "...", "..."]
}
```

이 구조는 Frontend 렌더링용이며 Story 원문 자체를 대체하지 않는다. Commit과 history에는 원문과 파싱 결과를 모두 보관할 수 있다.

## 8. Extract와의 관계

Extract는 Story 원문에서 다음을 별도로 반환한다.

- `dialogue_lines`
- `turn_summary`
- `choices`
- 상태 delta

`dialogue_lines` 예시:

```json
[
  {
    "speaker": "김하연",
    "direction": "자료를 내려다보다가 조심스럽게 고개를 들며",
    "text": "수정안은 봤어요. 그런데 이 부분은 대표님께 다시 확인해야 할 것 같아요."
  }
]
```

Frontend는 실시간 표시를 위해 Story marker parser를 사용하고, 저장·TTS·기록에는 검증된 `dialogue_lines`를 사용할 수 있다.

Extract가 일부 대화를 놓쳐도 이미 표시된 Story를 지우거나 재작성하지 않는다. warning만 기록한다.

## 9. TTS 계약

기본 대상:

- 등록 메인 NPC dialogue
- voice_id가 있는 발화자

기본 제외:

- SCENE
- PLAYER_STATUS
- CHOICES
- narrator
- 플레이어 입력
- voice_id가 없는 일반 NPC

여러 대사가 있는 경우 Story 순서대로 queue에 넣는다.

## 10. 다중 NPC 장면

- 모든 DIALOGUE 블록에 speaker가 있으므로 발화자 혼동을 줄인다.
- 이미지 패널은 마지막 발화자가 아니라 현재 focal character를 따로 결정한다.
- 일반 NPC는 등록 프로필 이름만 사용할 수 있다.
- 주변 군중의 짧은 반응도 대사라면 speaker가 필요하다.
- 익명 집단 반응은 SCENE에 서술하고 임의 화자명을 만들지 않는다.

## 11. 형식 실패 fallback

모델이 marker를 일부 어긴 경우:

1. 이미 인식한 정상 블록은 유지한다.
2. 인식하지 못한 나머지는 `unparsed` scene block으로 표시한다.
3. 원문을 삭제하지 않는다.
4. Story 재생성이나 repair 모델 호출을 하지 않는다.
5. 선택지 4개가 파싱되지 않으면 직접 입력은 계속 허용한다.
6. warning을 로그에 남긴다.

## 12. 기록 화면

플레이 기록은 기본적으로 다음 순서로 표시한다.

1. 플레이어 행동
2. 서사·대화 블록
3. 턴 요약
4. 다음 선택지

대화만 모아보는 필터는 추후 기능이며 초기 필수 기능이 아니다.

## 13. 프롬프트 지침

Story 모델에는 다음을 명확히 요구한다.

- SCENE과 DIALOGUE를 시간 순서대로 번갈아 출력
- 대사는 SCENE에 섞지 않음
- 인물 행동과 실제 발화를 구분
- 모든 DIALOGUE에 speaker/direction 포함
- 플레이어가 말하지 않은 대사를 대신 작성하지 않음
- 마지막에 PLAYER_STATUS와 CHOICES 출력
- marker 이름을 변형하지 않음

## 14. 정적 테스트

필수 계약 테스트:

- SCENE 단일 블록 파싱
- DIALOGUE speaker/direction 파싱
- SCENE/DIALOGUE 반복 순서 유지
- streaming chunk가 marker 중간에서 잘리는 경우
- 대사 따옴표가 여러 chunk로 나뉘는 경우
- malformed marker fallback
- PLAYER_STATUS 분리
- CHOICES 정확히 4개
- dialogue-only TTS queue
- 원문 보존

## 15. 수용 기준

- 사용자는 서사와 캐릭터 대화를 시각적으로 즉시 구분할 수 있다.
- 장면의 시간 순서가 분리 때문에 깨지지 않는다.
- 다중 NPC 장면에서도 모든 실제 발화의 주체가 명확하다.
- TTS가 서사 대신 캐릭터 대사만 읽을 수 있다.
- marker 일부가 깨져도 Story 원문과 플레이 진행이 보존된다.
- 형식 오류로 추가 LLM 호출이나 Story 재작성을 하지 않는다.

## 16. 금지

- 서사를 모두 출력한 뒤 대화만 한꺼번에 별도 목록으로 모으지 않는다. 시간 순서가 깨진다.
- 캐릭터 대사를 단순 정규식만으로 추측하지 않는다.
- 화자 없는 따옴표 대사를 허용하지 않는다.
- UI 렌더링 편의를 위해 Story 원문을 변조해 Commit하지 않는다.
- marker 파싱 실패를 이유로 Story 전체를 실패 처리하지 않는다.
